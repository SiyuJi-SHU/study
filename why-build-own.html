为什么自研 Totoro

1一句话和流程
一句话

边界 → 三个缺口（版本 / 扩窗 / 归因）→ 收缩范围 → LangGraph 对照 → 代价

2完整回答

先说清边界：Dify 解决的是快速搭起来，我自研解决的是跑起来之后能不能复现、能不能归因。如果只是快速上线，我直接选 Dify，应用编排、知识库、工作流它都成熟，这部分我不重复造。

我真正要的是三个 Dify 不方便控制的点。第一，版本要一起固定，Agent 配置、知识版本、检索配置和题集绑定，历史 Run 和评测结果才能复现。第二，检索命中后要回不可变原文扩窗、程序绑定引用，框架不负责文档版本和 offset。第三，失败要能定位到召回、重排、证据还是生成，这是业务语义，框架只给 tracing。

所以范围缩到四块：Runtime、工具网关、RAG 证据链、评测。不做可视化编排，不做模型托管。

对照 LangGraph：它用图表达控制流、用 Checkpoint 存状态；我的控制流是业务固定的三种模式，状态存在 Session、Run、run_events 里，所以没引入图执行器。

代价是维护成本高、开箱能力不如 Dify，目前单机 Compose，不是高可用平台。一句话：框架解决怎么搭，我解决怎么可复现、可归因。

3可能被追问
  • 什么时候你还是会选 Dify？→ 快速上线、不需要版本强绑定和失败归因时，直接用现成的。
  • 为什么不把 LangGraph 引进来？→ 流程固定三类，状态已落库，没有时间旅行和动态图需求，引入反而重。
  • 付出什么代价？→ 维护和迭代都自己做，单机 Compose，非高可用。
缺口

没做断点恢复 / 时间旅行，单机非高可用，要主动说清，别被追着打。
