1

意图识别怎么做

1一句话和流程
一句话

意图识别是分类，路由是分发；按能力规模选方案，少用 FC、多用两级

方案什么规模用代价
① 结构化 Function Call工具只有几个描述全进上下文
② 提示词分类能力固定，十几二十个意图写死，加一类就要改 prompt
③ RAG 分类能力几百个多一次检索，延迟上升
④ 微调小模型本地、要快、意图稳定要标注，意图变了要重训
为什么会换方案
预算一个工具定义约 100 到 200 token；100 个就是 1 到 2 万，ReAct 每轮还要重发
准确率候选越多，相近工具越容易混；20 到 30 个之后明显下滑
成本路由是高频动作，全量工具每次都带，延迟和费用都翻倍
补充

Jev 是 TypeSafe AI 2026 年 9 月发布的 System One 模型，作者是 InstructGPT 的合著者 Diogo Almeida。它就是拿来干意图识别的：你给它一段状态和一组带类型的问题，它从选项里选一个，并给出置信度。

它不生成文字，答案形状提前固定，所以编不出内容；官方说比聊天模型快 20 到 200 倍、便宜 40 到 400 倍，单次决策约 0.0004 美元。

本质是 typed decision，意图识别只是最典型的场景；开源版叫 Lev，4B 参数，可本地跑。分工是它做快筛，置信度低或新意图交给大模型仲裁。

2完整回答

意图识别就是判断用户这句话想干什么。它和路由不是一回事：意图识别是分类，路由是把请求分发给谁。

能力只有几个的时候，直接用结构化 Function Call：模型在工具列表里选一个，顺手把参数填好，这就是意图识别。

能力到十几二十个，比如酒店有订房、退房、洗衣、续住，就用提示词分类：类别写进 prompt，模型只输出一个枚举，再按枚举分发给对应的子 Agent，这一步叫解耦。

能力到几百个，全塞进上下文会撑爆，就上 RAG 分类：先按语义召回 TopK 个候选能力，再让模型在候选里选。这是两级，先筛后判。

如果要求本地、低延迟、意图又稳定，就训一个专用小模型，或者用 Jev 这类结构化决策模型：输入是问题加最近几轮，输出是意图标签和置信度。代价是意图集合固定，加一个就要重训。

一句话：能力少用 FC，能力多用两级，要快就微调。

我项目里用的是第二种。一次低温调用，temperature 0、maxTokens 400，system 里把 6 个 task 和 5 个 basis 的枚举、边界和例子写清楚，让模型只输出 task、reason、basis 三个字段，程序只认枚举，不认自由文本。解析失败先重试一次，还失败就降级成需要澄清，宁可多问一句也不猜。

拿到结果后还有四道规则兜底：没有历史却判成追问、问候却带了通识、闲聊却要求取证、诊断或问当前时间，都会被纠正。

basis 决定后面的执行策略：NONE 不查，GENERAL 可以用通识，SOURCED 必须取证，MIXED 两者都要，TRANSFORM 直接改写上一条。意图本身不决定执行模式和权限，那是 Agent 版本里固定好的。

3我项目里的代码

① Router 只输出这三个字段：

{"task": "KNOWLEDGE_QUESTION", "reason": "用户在问报销流程", "basis": "SOURCED"}

② 规则纠正在 TaskRouter 里兜底：

if (task == Task.FOLLOW_UP && history.isEmpty()) task = Task.CLARIFICATION_NEEDED;
if (task == Task.GREETING) basis = Basis.NONE;
if ((basis == Basis.GENERAL || basis == Basis.MIXED) && task == Task.CASUAL_CHAT) task = Task.KNOWLEDGE_QUESTION;
if (task == Task.INCIDENT_DIAGNOSIS || currentTimeQuestion(question)) basis = Basis.SOURCED;
4可能被追问
  • 意图识别和路由什么区别？→ 分类 vs 分发。我的 Router 只出枚举，执行模式由 Agent 版本决定，意图不能改权限。
  • 能力几百个怎么办？→ 两级：先召回候选能力，再让模型在候选里选；我现在是单级。
  • 微调什么时候值得？→ 本地、低延迟、意图稳定；代价是标注和重训。
  • 分错了怎么办？→ 格式重试一次，规则纠正，最后降级澄清，再加评测兜底。
  • Router 和主模型共用上下文吗？→ 不共用。Router 只看问题、最近回答 1600 字和附件目录；判断意图不需要全量上下文，给多了反而干扰分类。
  • 这个方案是主流的吗？→ 是，叫 router pattern 或 query understanding。LlamaIndex 的 RouterQueryEngine、LangGraph 的条件边、semantic router 都是同一个思路。
  • 工具只有 8 个，为什么还要意图识别？→ 它不是为了选工具，是为了定策略。没有它的时候检索是前置的，问候也会先查一遍，慢而且不可控；有了 basis，NONE 直接不查、SOURCED 必须取证，策略显式、可配置、可评测。
  • 那把工具调用改成 auto 不就行了？→ auto 只是允许不调，模型仍然可能调，同一个问题两次行为还可能不一样。我要的是确定性和可度量：路由准确率能单独统计，auto 给不了。
缺口

我没做两级路由，也没训专用分类模型；能力规模上去要补召回层。
