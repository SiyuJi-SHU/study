什么是 SSE

1一句话和三层
一句话

打字机只是现象；SSE = 消息格式 + HTTP 分块传输 + 客户端接口，三层分开说才不会乱

层是什么关键点
消息格式响应头 text/event-streamdata / event / id / retry + 空行分隔
传输HTTP 分块传输，边生成边吐和消息格式不是一回事
客户端EventSource 只支持 GET换 fetch 读流，POST 照样能流
2数据长什么样
一次流式回答，实际在网络上滚过去的就是下面这种东西：
event: token
id: 12
data: {"delta": "今天"}

event: token
id: 13
data: {"delta": "天气很好"}

event: done
id: 14
data: {"finish_reason": "stop"}
四个字段

- data: 后面冒号跟一个空格，再跟内容；JSON 要压成一行，不能换行，否则会被截断成多条。

- 空行（也就是两个 \n）是一条消息结束的边界，前端收到空行才真正派发事件，这是最容易写错的地方。

- event: 事件类型，AI 场景里用来区分 token 增量、工具调用、阶段状态、错误、结束。

- id: 事件序号，断线重连时浏览器会自动把它塞进 Last-Event-ID 请求头。

- retry: 重连间隔毫秒；还有一种写法是 : ping，冒号开头是注释行，常拿来当心跳。

3完整回答

SSE 就是服务端往客户端持续推文本。很多人第一句说"打字机效果"，那只说了现象，没说机制。我一般拆成三层：格式、传输、客户端。

格式这一层，响应头声明 text/event-stream，每条消息以 data: 开头，字段可以有 event、id、retry，两条消息之间用一个空行隔开。空行才是"这一条结束"的信号。

传输这一层，底下就是 HTTP 的分块传输，模型吐出几个字就往外发几个字，所以用户不用等全部生成完。

客户端这一层，有个流传很广的说法——"SSE 只支持 GET"。这句话对一半：受限的是浏览器原生的 EventSource 接口，它不能 POST、不能带自定义请求头。但你换成 fetch 自己读流，POST 完全没问题。OpenAI、DeepSeek 的流式接口就是 POST 返回 text/event-stream。

所以结论是：SSE 不但能用，它就是大模型流式的默认方案。真正要小心的是工程上的三个坑——反向代理默认会缓冲、HTTP/1.1 同域连接数有限、长连接要心跳。

最后多模态要说清楚在哪一层问：传输层什么字节都能传；SSE 消息层是文本，图片得 base64 内联，或者只发 URL 让前端自己取。

4可能被追问
  • 为什么不用 WebSocket？→ 这条链路只要服务端到客户端的单向流，SSE 基于 HTTP，自带重连，鉴权能沿用网关那一套；WebSocket 双向，但心跳、重连、代理兼容都要自己维护。
  • "所有 SSE 都是假的，都是 streamable 模拟的"这话对吗？→ 不对。streamable 不是标准术语，说的是 HTTP 的分块传输；分块传输是传输层，SSE 是消息格式，两者本来就是一个下、一个上，不是替代关系。另外 MCP 里那个 Streamable HTTP 是另一个概念，别混。
  • 图片能不能用 SSE 推？→ 消息层是文本，二进制要 base64 内联或只给 URL；工程上一般只推一句"图片已生成"，地址给前端自己拉。
  • 断线了怎么办？→ 见下一张卡：靠 id + Last-Event-ID + 落库补发。
缺口

HTTP/1.1 下同域连接数有限，多标签页会互相抢占，这块没做连接合并；反向代理的响应缓冲也没显式关闭。
