Totoro 这个项目，你为什么要自己做？

因为我想展示我个人对于整个 Harness 的理解。因为 Harness 无非就是包括一个完整的 agent loop，里面会加入各种各样的工程化思想。所以我从零做了这个完整的项目，把它走了一遍：

一是上下文管理；

二是意图识别；

三是整个后端能够自主配置 Agent、自主创建知识库；

四是完整的评测链路。

这四块都是我自己设计的。比如 Agent 跑一次，用哪个版本、哪些资料、哪些工具、花多少预算，都是 AgentRuntime 管的；每次运行都落在 PostgreSQL 里，所以答错了，我能查到是哪一次运行、用的哪个版本、检索到了什么。

我对这个链路很感兴趣，它在我生活里也确实用得上。现在 AI 写代码的能力很强，只要我把 Agent 的各个模块搞清楚，就能把整个项目做出来。所以我就动手做了，从零开始全栈开发，从架构到后端到评测都是我一个人做的。

被追问时讲 · AgentRuntime 具体怎么跑

一次运行，从进来请求到落库，都是 AgentRuntime 管的。

先钉死这次要用的东西。会话绑定的 Agent 版本、知识库范围、允许调的工具、现场快照，还有这次的附件，一起存成一个 Context。后面整个过程都用这一份，中途有人改了配置，也不影响这次运行。然后排队、设截止时间，队列满了直接返回 429，超时就整次标成 timed_out。

第一步是意图识别。TaskRouter 判断这是闲聊、追问、要读附件、缺材料要澄清，还是知识问题。意图只决定走哪条路，不决定用哪个执行器。执行器只看配置里钉死的模式：ReAct、计划执行，还是固定流程。

进到执行器就是 agent loop。模型自己选工具，工具调完把结果加回上下文，再决定下一步。有工具调用次数上限，也有轮次上限。每次工具调用前后都发事件，前端按序号往前推。

上下文的摆法是有讲究的。用户这句话放在检索到的资料后面，防止资料把用户的原意盖掉。检索回来的内容、工具返回、历史对话，都当成不可信数据写进 Prompt，防止资料里夹带的指令把 Agent 带跑。

模型交上来的答案不能直接给用户。先用程序校验：引用的证据是不是这次真拿到的，命令和报告格式对不对，不合规的项直接删。删完还有问题，就让模型做一次引用修复，只改引用，不改结论。最后按情况给状态：completed、partial、insufficient_evidence、validation_failed。结果、证据、计划、模型用量，全部落 PostgreSQL。
