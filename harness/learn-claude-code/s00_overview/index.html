s01 · Agent Loop

  • 加了什么：一个 while 循环 + 一个 bash 工具，30 行代码
  • 为什么需要：之前把问题发给模型，它只能输出一段文字就结束——能"说"要执行 ls，但不能真去执行。你得自己跑命令、把结果贴回对话框，每个来回你都在当中间层
  • 总结：s01 把这个人肉中转写成代码。模型每轮回答里如果带 tool_use，循环就替它执行 bash 命令，把输出作为 tool_result 追加回 messages，再全量发给模型；这轮没有 tool_use，说明模型认为任务完成，循环退出
  • messages 是什么：一个只增不减的列表——用户问题、模型回答、工具结果，全部 append 进去。每轮把完整 messages 全量重发给模型（system prompt 和工具描述也每次都带），模型据此决定下一步
  • 边界：只写了循环本身，没做任何上下文管理，messages 会一直涨到 token 上限

s02 · Tool Use

  • 加了什么：新增 4 个专用文件工具（read_file / write_file / edit_file / glob），加 bash 共 5 个；外加一张 TOOL_HANDLERS 分发字典
  • 为什么需要：只有 bash 时，读文件要 cat、写文件要 echo >、找文件要 find——命令又长又容易错。专用工具参数明确、输出稳定，模型用起来不容易翻车
  • 总结：循环一个字没改，改的只是执行那一行——s01 写死 run_bash，s02 换成按工具名查字典分发（TOOL_HANDLERS[block.name]）。以后加工具，只需要往两张表里各加一条，循环永远不动
  • 两张表是什么：TOOLS（schema：name + description + 参数定义）发给模型，让它知道有什么工具、怎么调；TOOL_HANDLERS（名字 → 实现函数）留在本地，负责真正执行。两拨受众不同，靠 name 对上——接口名给模型看（短、符合训练语料习惯），函数名是本地实现，故意解耦
  • 边界：模型输出的工具名是不可信字符串，查字典本身就是白名单——字典里没有的直接回 "Unknown"，永远不会执行到别的函数。safe_path 还把文件工具锁在工作目录内，路径逃不出去

s03 · Permission

  • 加了什么：在"模型报出 tool_call"和"真正执行"之间，插入一段后端写死的检查流程——三道闸门，按顺序过
  • 为什么需要：工具是通用的。bash 里 ls、rm -rf /、git push 全塞在同一个工具里，拦的从来不是工具本身，而是这一次具体的调用（工具名 + 参数）。所以没法在设计 TOOLS 时定死——总不能给每条命令单独做一个工具
  • 闸门一：黑名单：硬编码的绝对危险名单（rm -rf /、sudo、shutdown）。命中直接杀，不问人。它是开发者写死在代码里的安全底线，用户配置改不掉——就算用户的规则表配错了，这些命令也永远出不了第一道闸
  • 闸门二：规则表：用户自己配的"预先批准"名单，比如"所有 git 只读命令放行"。命中就自动放行，不再弹窗。没有它，模型每跑一条 ls 都要问人，用户会被烦死
  • 闸门三：问人：前两道都不命中——既不明确危险、也没预先批准——循环在这里阻塞，终端弹 y/n，人来拍板。同意则执行，拒绝则走拒绝回流
  • 顺序即优先级：三道闸的先后顺序，就是"deny 压过 allow"的实现。就算合并成一张表，也得另写一套"拒绝条目压过放行条目"的排序逻辑——等于绕一圈把两道闸又造出来。分开，反而最直白
  • 拒绝怎么回流：被拦的调用不是悄悄丢掉。协议硬要求每个 tool_use 必须有对应的 tool_result，所以 harness 会伪造一条 "Permission denied." 的 tool_result 塞回 messages——模型必须知道被拒了，才能换路走
  • 对应 Claude Code：settings.json 里的 permissions.allow / deny / ask 三张列表，就是这三道闸

s04 · Hooks

  • 加了什么：一张 HOOKS 注册表（事件名 → 钩子函数列表）+ 循环里四个固定的事件触发点。循环本体从此不再为任何新功能改动
  • 为什么需要：s03 暴露了病根——权限检查是直接缝在循环里的。以后想要"每次 bash 留日志"、"写完文件自动 git add"，每加一个功能就得往循环里动一次手术，而循环是最核心、一崩全完的代码。s04 把"加功能"从"改循环"变成"往插座上插插头"
  • s04 为止的循环形态：①用户输入 →【UserPromptSubmit】→ ②全量 messages 发给模型 → ③模型回答 → ④没有 tool_calls 就【Stop】（没人拦则结束）；有则每个调用依次：【PreToolUse】→ ⑤执行工具（TOOL_HANDLERS 查表分发）→【PostToolUse】→ ⑥结果 append 回 messages，回到 ②
  • 钩子是什么：一个普通函数 + 一个注册动作。到点自动被调，拿到现场信息（工具名 + 参数），返回一个决定。循环只负责喊"事件到了"，不关心谁在听、听到之后干什么
  • PreToolUse（执行前）：三个动作——拦截（跳过执行，伪造 "Permission denied." 回流）、改写（把参数改安全了再执行）、放行。s03 的三道闸门在 s04 里就变成一个 PreToolUse 钩子：功能不变，位置从"焊死在循环里"变成"插在插座上"
  • PostToolUse（执行后）：记录每次 bash 调用的日志、write_file 之后自动 git add，都是这里的典型住户
  • UserPromptSubmit（用户话音刚落）：往消息里注入额外上下文（今天日期、项目信息），或过滤敏感内容
  • Stop（语义是反的）：其他三个钩子是"某事发生时顺便干点什么"；Stop 是"模型说做完了想走"时，钩子可以一票否决——"todo 还没清完，继续干"
  • 钩子不是工具：工具写在 TOOLS 里发给模型看，由模型自己决定调不调；钩子模型完全看不见，由人注册、到点必然执行。模型对钩子没有发言权
  • 一句话：s04 没有新增任何能力，它改变的是能力的挂载方式——从焊死（改循环）到可插拔（注册）。循环从此是冻结的底座，后面十几章的机制尽量都挂在事件点上，不再碰循环本体

s05 · TodoWrite

  • 加了什么：一个叫 TodoWrite 的工具——全家唯一"什么都不执行"的工具。不读文件、不跑命令，唯一的动作是把模型写的任务清单作为一条文本 append 到 messages 末尾
  • 为什么需要：长任务会跑偏。计划写在第一条用户消息里，后面几十轮工具输出不断 append，把它越埋越深；而模型注意力最重的恰恰是最近的上下文——干到第四步时，眼前全是第三步的工具结果，第一条里的计划早就沉底了。于是忘步骤、重做已完成的事
  • 怎么用：模型接活先调 TodoWrite 列清单，每干完一步就回来更新一次——勾掉完成的、补上漏的。每次更新 = 在 messages 最末尾贴一条"最新版计划" = 把计划推回注意力最强的地方。旧的那份还埋在底下，无所谓，最新这条在最上面
  • 用上下文对抗上下文：问题（计划被新增上下文淹没）和解法（把计划作为最新上下文再发一遍）用的是同一个机制，一攻一守。没有发明任何新东西
  • 纯软约束：没有任何代码检查"是否照清单行事"，清单的效力全部来自模型看到自己写的清单、倾向于照着执行。硬约束在 s03（闸门拦你），这里是自己管自己；s04 的 Stop 钩子（"todo 没清完不许结束"）是给这个软约束上的硬保险
  • 它是工具，不是钩子（跟 s04 对照着记）：TodoWrite 模型看得见、自己决定调、想写什么写什么；钩子正相反——模型看不见、人注册、到点必跑
  • 边界：治标不治本——一个字节都没减少上下文，messages 照样涨到 token 上限，治本（压缩）要等 s08。Claude Code 里真有这个工具，一模一样的原理

s06 · Subagent

  • 加了什么：一个叫 task 的工具。对父循环来说它就是个普通 tool call——schema 在 TOOLS 里、走 TOOL_HANDLERS 分发，跟 bash 没任何区别。玄机全在它的 handler 里：别的 handler 几毫秒返回，task 的 handler 却开一个全新 messages[]、跑一整个嵌套 agent loop（s01 循环再实例化一份），跑完只把最终文本作为 tool_result 交回父对话
  • 为什么需要：主 agent 追一个调用链要读一堆文件，每次工具结果全 append 进父 messages；调用链理清后这些中间细节就没用了，却永远占着上下文。s05 是对抗（把计划浮上来），s06 是隔离——脏活压根别在主上下文里干
  • 外包类比：父是部门经理，子是实习生。把一件明确的杂活外包出去，实习生翻多少资料、试错多少次你不用看，你桌上只多一页结论——父上下文只进一条结果，几十轮中间过程全挡在外面
  • 只隔离消息，不隔离文件系统：父子共享同一个工作目录、同一个进程，子 agent 写的文件、跑的命令，父全看得见、受影响。隔离的是"聊天记录"，不是"工作区"。反着记：子干的活是真实的，只是唠叨被消音了
  • 子工具表里没有 task：子只拿五个基础工具，唯独不含 task——不能再派孙 agent，委派只允许一层，防无限套娃。另有 30 轮上限兜底，超了就返回"没能在 30 轮内给出答案"
  • 权限和钩子是同一套：子的每次工具调用照样过 s03 的三道闸门、触发 s04 的钩子——外包出去，不等于脱离监管
  • 三章对照：s05 对抗上下文（计划浮上来）/ s06 隔离上下文（脏活去别处干）/ s08 压缩上下文（治本）——同一个战场的三种打法。父循环自始至终不知道 subagent 存在，嵌套循环完全藏在 tool handler 里，循环本体零改动
