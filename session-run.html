2完整回答

Session 是一段多轮对话的容器，但价值不只在容器：创建时就固定 agent_version，这段对话之后所有 Run 都用这个版本；还带 origin，区分用户、调试和评测。

Run 是容器里的一次请求，有自己的输入、上下文、结果、错误和状态。它落在 PostgreSQL：agent_runs 一行一次运行，run_events 一行一个事件，主键是 run_id 加 sequence。所以对话记录是持久化的行，不是内存里的消息数组。

它和上下文是两回事。上下文是每次请求临时拼出来喂模型的，只取最近四条有结果的运行，按 1600、8000、24000 三档截断；Session 里是全量。模型看到的是摘要，库里留的是全量。

Run 里另存一份本次运行的上下文快照，不是完整提示词：知识范围、现场快照、工具白名单、附件清单。下一轮请求要靠它继承现场和附件。

Run 从 queued 到 running，需要最终校验时进 reviewing，终态是 completed、partial、cancelled、failed、timed_out，另外证据不足和校验不过也各自落一个状态。同一 Session 只允许一个活动 Run，代码里两层：部分唯一索引只对 queued、running、reviewing 生效，创建时再锁 Session 行查一次，冲突返回 409。前者防脏数据，后者给用户明确提示。

拆开是因为只存 user 和 assistant 消息，答不了当时用的哪个版本、调了什么工具、为什么失败。拆开以后一次失败不污染会话，还能独立取消、计量、回放，Run 本身也是评测单元。

4可能被追问
  • Session 和上下文记忆有什么区别？→ 上下文是临时拼给模型的摘要，Session 是库里的全量记录。
  • 对话记录存在哪？→ 结构化记录全在 PostgreSQL；原文和附件在文件存储，向量在 Milvus，不在 PostgreSQL。
  • 对话越聊越多会不会撑爆 PG？→ 存储线性涨，延迟不线性涨：读路径只取最近几条，事件也限 200 条；先疼的是磁盘和事件表膨胀。
  • 唯一活动 Run 是数据库约束还是应用约束？→ 两层：部分唯一索引兜底，创建时锁会话行检查后返回 409。
  • Run 的终态有哪几种？→ completed、partial、cancelled、failed、timed_out，另有证据不足和校验不过。
  • 为什么 Run 也存 agent_version？→ 追溯粒度是 Run，一行就能看出这次用的是哪个版本。
  • 只存对话消息为什么不行？→ 丢掉了版本、工具调用和失败原因，没法复现和归因。
  • 为什么限制同一 Session 只有一个活动 Run？→ 状态一致，避免并发写乱，也能独立取消和计量。
缺口

run_events 没有 TTL 或归档，只有删 Agent 时级联删；没有跨会话记忆；状态机要讲顺，这是数据建模和评测单元的双重考点。
