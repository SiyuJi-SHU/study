SSE 断线续接

1一句话和三层
一句话

这题不考什么是 SSE，考断了还能不能接上：先落库再推 → sequence 游标 → after 补发 → 幂等去重

层靠什么解决什么
协议层事件 id + Last-Event-ID浏览器知道从哪条续
业务层事件落库 + 递增 sequence重启、换实例还能补
体验层前端记游标 + 占位 + 重试不重复、不缺段、不干等
2一次断线长什么样
正常的流，每条事件都带 id；断开时前端只记住最后收到的那条：
event: token
id: 12
data: {"delta": "今天"}

event: token
id: 13
data: {"delta": "天气"}

← 这里网络断了，前端最后收到 id: 13
重连时把游标带回来，服务端只补大于它的事件：
GET /api/runs/123/events?after=13
Last-Event-ID: 13

-- 服务端
SELECT * FROM run_events
 WHERE run_id = 123 AND seq > 13
 ORDER BY seq
3完整回答

这题考的不是 SSE 是什么，是它断了以后还能不能接上。场景很具体：用户切到后台，或者网络抖一下，流就断了，前端只收到半句话。重连之后一般会出现三种病：答案重复、答案缺一段，或者干脆从头重新生成，token 白烧一遍。

我的方案，第一句就是：先落库，再推送。每个 Run 的事件写进 run_events 表，主键是 run_id 加递增的 sequence；SSE 只负责把新事件推给浏览器，不承担"记住历史"这件事。

断线之后，前端记住自己最后消费到的 sequence，重连时带着 after 重新订阅，服务端只查比它大的事件。浏览器的 Last-Event-ID 请求头也可以当这个游标用。因为事件已经在库里了，哪怕进程重启、换一台机器，照样能补。

不重复这件事，我靠两手：客户端按 sequence 幂等去重，重复收到的直接丢；已经推过的 token 不重算——重算意味着再调一次模型，成本和结果都会对不上。

体验层再补一刀：断了以后前端先占位、给一个手动重试，别让用户对着半句话干等。

最后说边界。如果事件只在内存里，重连就只能从头重生成。所以断线续接的前提，是这次 Run 的事件可回放——这就是"落库"和"不落库"的分水岭。

4可能被追问
  • 为什么不用 WebSocket？→ 这条链路只有服务端到客户端的单向流；SSE 建立在 HTTP 上，浏览器自带重连，网关鉴权能沿用。WebSocket 双向，但心跳、重连、代理兼容都得自己维护。
  • 不落库行不行？→ 行，但断线只能从头重生成，既浪费 token，也可能两次答案不一致。
  • 多实例部署怎么办？→ 事件流要放共享存储（库或 Redis），纯进程内存扛不住重启和横向扩容。
  • 客户端怎么知道自己漏了哪条？→ 记 last seq，或用服务端下发的 Last-Event-ID；服务端按 seq 严格递增，就不会出现乱序。
  • 事件表会不会无限膨胀？→ 按 Run 定期归档或设保留期，只保留最近 N 条给重连用。
缺口

"先落库再推"要作为第一句讲出来，这是和不落库方案的本质区别；另外事件保留期、多实例下的共享存储，要能说清有没有做。
