一次请求的完整链路

1一句话和链路
一句话

一次请求就是定版本、判任务、取证、校验、落库；我在版本、任务、证据三点做了收敛，让每条回答可追溯、可核对。

2完整回答

这条链路和主流 Agent 的骨架是一致的：路由、执行、取证、校验、落库和观测。我在这条骨架上做了几个收敛，按三段讲。

第一段是版本。用户消息进来先落到 Session，Session 在创建时就固定了 agent_version——模型、提示词、工具权限、执行模式都是这个版本里的配置。之后每次请求创建 Run，Run 直接绑定这个版本。所以中途在后台改配置，是插一个新版本行，只影响新开的对话，旧对话继续用旧版本，前提是旧版本还在、Agent 没停用。这样做的好处是任何一条历史回答都能追溯到当时的配置。

第二段是任务。版本定完走 Router，它是一个低温 LLM（temperature 0），只输出两件事：任务类型和判断依据，不选执行器——执行模式由版本配置里的 strategy 定死。然后创建 Run，这里我用了双重约束防并发：先对 Session 行加行锁再查有没有活动 Run，数据库还有一个部分唯一索引兜底，保证一个 Session 同时只有一个活动 Run。之后按模式进 ReAct、Plan 或 Workflow。

第三段是证据。检索支持向量、关键词、混合三种模式，混合是两路候选做 RRF 融合再重排，分数过 0.15 才保留。命中的小块会自动扩到 6000 字的原文窗口，每条证据带唯一 ID，模型回答时只能选给定的段落号，程序回填引用并做校验，校验不过最多修复一次。最后答案、引用、工具调用全部写进 PostgreSQL 的 run_events，通过 SSE 推给前端。

两个容易误解的点：一是知识问答不是逐字流式，答案是结构化校验通过后才整体发出，闲聊和改写场景才有逐字流；二是 Router 只做任务判断，不参与选执行模式。

总结就是三个取舍：Router 不选执行器，Plan 和 Workflow 收敛成单 Agent 控制流，知识答案校验之后才展示。

4可能被追问
  • 所以是没有流式输出吗？→ 不是。知识问答是结构化 JSON 校验通过后才发 answer_text，不逐字流；问候、闲聊、改写走 streamText，有 answer_delta 逐字流；SSE 过程事件一直都在。
  • 固定版本就等于答案可复现吗？→ 不等于。固定的是配置；模型服务、知识内容、检索参数变了，答案还会变。
  • 旧版本什么时候会用不了？→ 版本被删、Agent 停用、schemaVersion 不兼容，任一成立旧对话就失败或只读。
  • Router 为什么不顺便选执行模式？→ 执行模式是工程决策，不是语言理解；交给版本配置比交给模型稳定、可回归。
  • 同一 Session 同时提问会怎样？→ 先锁 Session 行再查活动 Run，第二个请求被拒；部分唯一索引是数据库层的兜底。
  • 检索命中就够了？→ 不够。小块只负责定位，命中后扩 6000 字原文补上下文，模型只能从给定段落里选。
  • 校验不过怎么办？→ CitationRepair 最多修一次，仍不过就是 validation_failed，不伪装成正常答案。
  • 前端断线了会重跑吗？→ 不会。SSE 只按 Last-Event-ID 补历史事件，任务不自动续跑。
缺口

并发锁竞争只在功能上验证过，没做压测数据；校验失败率、CitationRepair 的挽回比例没统计；SSE 断线只做到事件回放，没做任务续跑。

边界

这条链路是单 Agent 的，没有跨进程 Agent 调用；知识问答的流是事件流，不是 token 流。
